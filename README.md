# 세금계산서 공급가액 합산 프로그램

카카오톡으로 전달받은 세금계산서 사진 여러 장(6~9장)에서 '공급가액'을 자동으로 인식해 합계를 계산하는 프로그램. 로컬 vision LLM(Ollama)을 이용해 사진 속 텍스트를 읽고, 세금계산서의 산술 규칙을 이용해 자동으로 결과를 검산한다.

## 왜 로컬 모델(Ollama)을 쓰는가

세금계산서에는 사업자등록번호, 상호, 금액 등 민감한 정보가 담겨 있다. 이 정보가 외부 서버로 전송되면 안 되기 때문에, GPT-4V/Claude/Gemini 같은 클라우드 vision API 대신 **로컬 PC에서 완전히 오프라인으로 동작하는 Ollama**를 선택했다. 사진이 한 번도 외부 네트워크로 나가지 않는다.

## 사용한 모델

- `qwen2.5vl:3b` (Ollama)
- 내장 그래픽카드(GPU 가속 없음) 환경이라, CPU로도 돌아갈 수 있는 가벼운 모델 위주로 검토함
- `minicpm-v`(8B)도 함께 테스트했으나 손글씨 세금계산서에서 반복적으로 완전히 틀린 값(심지어 다른 언어가 섞여 나오는 등)을 냈고, 속도도 더 느려서 최종적으로 qwen2.5vl:3b를 선택

## 겪었던 문제와 해결 과정

### 1. 컨텍스트 크기 초과 에러
사진 한 장을 vision 모델에 넣으면 토큰 수가 수천 개까지 올라가는데, Ollama 기본 컨텍스트(4096)를 초과해 `400 Bad Request` 에러가 발생했다. `num_ctx` 파라미터를 8192 이상으로 명시적으로 늘려서 해결했다.

### 2. 터미널(REPL)에서 같은 사진을 새로 넣어도 답이 안 바뀌는 문제
`ollama run` 대화형 모드에서 이미지를 바꿔 질문해도 이전 답변과 완전히 동일한(혹은 여전히 틀린) 답이 반복되는 현상이 있었다. 원인을 좁히기 위해, 매번 대화 기록 없이 **완전히 새로운 요청**을 보내는 Python 스크립트(`ollama` 패키지의 `ollama.chat()`)로 테스트 방식을 바꿨다. 그 결과 같은 모델(qwen2.5vl:3b)이 원본 사진을 문제없이 정확하게 읽어내는 것을 확인했다 — 문제는 모델의 인식 능력이 아니라 REPL 세션에 대화 맥락이 누적되는 것이었다.

이 경험 때문에 프로그램은 처음부터 "사진 1장 = 완전히 독립적인 요청 1개"로 설계했다.

### 3. 손글씨 세금계산서에서의 오인식 (가장 큰 문제)
수기로 작성된 세금계산서 6장을 실제로 배치 처리해보니, 6장 중 2장에서 공급가액을 완전히 잘못 읽었다 (예: 실제 값이 두 자릿수 정도 낮게, 즉 자릿수를 통째로 날려서 인식되는 패턴). 단순히 모델 출력을 그대로 합산했다면 실제 합계보다 약 39% 낮게 계산될 뻔했다.

**해결책:** 세금계산서는 항상 `세액 = 공급가액 × 10%` 라는 고정된 산술 관계를 가진다는 점을 이용했다. 모델에게 공급가액과 세액을 **함께** 물어본 뒤, 두 값이 10% 관계를 만족하는지 스크립트가 자동으로 검산하도록 만들었다. 관계가 안 맞으면 그 사진만 "확인 필요"로 표시한다.

이 방식으로 6장을 전부 사람이 눈으로 볼 필요 없이, 실제로 의심스러운 사진만 걸러내서 확인하면 되는 구조를 만들었다 — 그리고 실제로 문제가 있었던 2장을 정확히 잡아냈다.

### 4. "확인 필요" 사진의 재시도(크롭) 단계
검산에 걸린 사진이 실제로 왜 틀렸는지 보니, 사진 전체를 통째로 주는 것보다 공급가액/세액이 적힌 표 부분만 잘라서(크롭) 주면 인식률이 크게 올라가는 걸 확인했다. 다만 매 사진을 다 크롭하는 건 자동화 취지에 맞지 않으므로, **검산에서 "확인 필요"로 걸러진 소수의 사진에 한해서만** 크롭한 버전으로 재시도할 수 있는 단계를 프로그램에 추가했다. 실제로 이 방식으로 6장 중 틀렸던 2장을 모두 정답으로 바로잡았다.

### 5. GUI 프레임워크 선택: Streamlit → Gradio
처음에는 Streamlit으로 GUI를 만들었다. 사진을 드래그해서 넣는 것까지는 잘 됐지만, 정작 원했던 핵심 기능인 **클립보드 붙여넣기(Ctrl+V)**가 Streamlit의 `file_uploader` 위젯에서는 지원되지 않는다는 걸 실제로 붙여넣기를 시도해보고서야 확인했다 (탐색기에서 파일을 복사해서 붙여도, 카카오톡에서 이미지 자체를 복사해서 붙여도 인식하지 않았다).

**해결책:** 클립보드 이미지 붙여넣기를 기본으로 지원하는 **Gradio**의 `Image` 컴포넌트(`sources=["upload", "clipboard"]`)로 GUI를 다시 만들었다. 로직(`ocr_core.py`)은 프레임워크와 무관하게 그대로 재사용하고, 화면 부분만 교체했다.

이 경험으로, GUI 프레임워크를 고를 때 "지원한다고 알려진 기능"이라도 실제로 그 프로젝트에서 필요한 상호작용 방식으로 직접 테스트해보고 넘어가야 한다는 걸 다시 확인했다.

### 6. 더블클릭 실행 아이콘(run.bat)이 아무 반응 없이 꺼지는 문제
터미널 대신 아이콘 더블클릭으로 실행할 수 있게 배치 파일(`run.bat`)을 만들었는데, 터미널에서 실행할 땐 잘 되던 게 더블클릭하면 창이 뜨자마자 사라졌다. 원인은 이 컴퓨터에 Anaconda가 두 곳(`C:\ProgramData\Anaconda3`, `C:\Users\{user}\anaconda3`)에 설치되어 있었고, 실제 패키지가 설치된 쪽은 시스템 PATH 환경변수에 등록되어 있지 않았던 것이었다. 터미널에서는 별도로 PATH가 잡혀 있어 문제없이 실행됐지만, 탐색기가 더블클릭으로 여는 프로세스는 레지스트리에 등록된 PATH만 봐서 `streamlit`/`python` 명령어를 못 찾고 즉시 종료된 것.

**해결책:** 배치 파일에서 명령어 이름 대신 **실제 실행 파일의 절대 경로**를 직접 지정해서, PATH 환경변수가 무엇이든 상관없이 항상 같은 파이썬 환경으로 실행되게 만들었다. PATH가 전혀 없는 환경에서도 정상 동작하는 것까지 확인 후 반영했다.

## 현재 상태 (1차 버전)

- `gradio_app.py` — GUI 버전. 사진을 드래그하거나 Ctrl+V로 붙여넣어 목록에 하나씩 추가하고, "합계 계산" 버튼으로 한 번에 처리
- `run.bat` — 더블클릭하면 `gradio_app.py`를 실행하고 브라우저를 자동으로 여는 실행 아이콘
- `calculate_total.py` — CLI 버전. 사진 경로 여러 개를 커맨드라인 인자로 받아 각각 공급가액/세액을 추출하고, 자동 검산 후 합계를 출력. "확인 필요"로 걸러진 사진은 크롭한 파일 경로를 입력해 재시도할 수 있음
  ```
  python calculate_total.py 사진1.jpg 사진2.jpg ...
  ```
- `ocr_core.py` — 모델 호출/파싱/검산 로직 (CLI, GUI 공용)
- `test_vision.py` — 모델 정확도를 실험할 때 쓴 테스트 스크립트
  ```
  python test_vision.py 사진.jpg
  ```
- `streamlit_app.py` — 초기 GUI 시도. 붙여넣기 미지원으로 Gradio로 대체했지만, 시행착오 기록 차원에서 남겨둠
